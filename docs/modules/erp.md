# ERP integration (module `erp`)

The ERP module is the machine-to-machine API that lets a supplier's ERP (today
the Orgasoft provider) push products and stock, read its orders, confirm or
reject them, and receive acknowledgements. The partner-facing contract is
`specs/002-erp-integration-api/contracts/openapi.yaml`; this page records the
module's entities, invariants and the rules a reader of the code needs.

## Entities

Schema `erp` (tenant-owned tables carry `organization_id`, row-level security on):

- `erp.integrations`: one per supplier; `status` is `active`, `paused` or `closed`.
- `erp.api_keys`: a key belongs to an integration; only `key_prefix` and a hash
  are stored. `status`, `expires_at`, `revoked_at` decide whether it authenticates.
- `erp.product_links`, `erp.sync_batches`, `erp.sync_items`, `erp.review_items`:
  product sync state (S2).
- `erp.order_imports`, `erp.idempotency_records`: order acknowledgement and retries (S3).
- `erp.api_calls`: call log, organization nullable for failed authentication.

## Customer codes (S5)

A buyer's customer code with a supplier is the organization number on its
`org.user_organizations` link to that supplier. The rules:

- A code is unique per ERP supplier. `GuardCustomerCode` refuses a code that
  another customer holds among pending and approved links. The same customer
  (its organization, or for a user-only link its user) may keep it.
- The guard and the link write run in one transaction under the supplier's
  advisory lock (`pg_advisory_xact_lock` keyed by the supplier). Two saves of the
  same code cannot both pass. The write runs through `database.JoinTx`, which
  makes nested `InTx` calls use the guard's transaction.
- A supplier without an active ERP integration and key is never asked for a code
  and never refused (SC-009).
- Codes compare trimmed and case-insensitively everywhere (`lower(trim(...))`):
  the guard, the order feed conflict check (`customerConflictSQL`) and the
  migration 257 index. Behaviour change in S5: the order feed now reports
  `code_conflict` for `C-1` against `c-1`, where it used to report two
  mapped customers.
- Existing duplicate codes stay as they are; the guard applies to new writes.

## Named exceptions to tenant isolation

Each is a function named `...AsSystem` or `...AsStaff` with a comment citing this
table (`plan.md` "Named exceptions"). Nothing else reads across tenants.

| ID | Function | Why |
|---|---|---|
| E1 | `FindKeyByPrefixAsSystem` | authentication happens before the tenant is known |
| E2 | `ListSalesShipmentsAsSystem`, `GetSalesShipmentAsSystem` | the buyer's order header is not visible to the supplier |
| E3 | `PurgeExpiredAsSystem` | retention job spans tenants |
| E4 | `InsertCallsAsSystem` | failed-authentication rows have no organization |
| E5 | `ListKeysAsStaff`, `RevokeKeyAsStaff` | staff oversight, behind the platform permissions |
| E6 | `ListOffersAsSystem`, `VariantOfferAsSystem` | supplier variants belong to other tenants |
| E7 | `ListPurchaseShipmentsAsSystem` | a buyer cannot see a supplier's shipments and lines |
| E8 | `SupplierERPStatusAsSystem` | a buyer cannot see a supplier's integration or key rows; returns booleans only |

## Platform helper added for S5

`database.JoinTx(ctx, tx, fn)` (in `internal/platform/database/join_tx.go`) makes
every `InTx` and `InReadTx` started inside `fn` run on `tx`. It is opt-in: only
`GuardCustomerCode` uses it, so no other transaction changes behaviour.

## Purchase orders (S7)

- `GET /erp/v1/offers?barcode=` lists up to 50 supplier offers (named exception E6), cheapest first.
  The unit price is the website's price: the public price less the discount percentage.
- `POST /erp/v1/orders/purchase` places the order through `erp.PurchasePlacer`. The adapter
  (`cmd/server/erp_purchase_placer.go`) quotes the lines, compares any sent `unitPrice`, and
  checks out through `commerce.CheckoutAPI`. The service checks the offer, the self-supply
  rule and the supplier link first, and compares the sent price with the offer, so a wrong
  price writes no order.
- Idempotency (`erp.idempotency_records`, scope `purchase_order`): the first call inserts an
  `in_progress` row. A finished row replays its stored order with HTTP 200. A refusal (4xx)
  deletes the row, so the ERP can retry. A crash leaves the row in progress; after 2 minutes
  the order is found by its note marker `[ERP:<provider>:<externalReference>]`, which the
  placer writes first in the order notes. The same reference with a different body is
  `ERP_IDEMPOTENCY_CONFLICT`.
- The creation writes the audit row `erp.po.create` (actor kind `api_key`) in the same
  transaction as the finished idempotency row. The order itself is written by the checkout.
- No account, link or customer is ever created by a purchase call (FR-031).

## Masked values and reveal (S8, FR-032)

- Sensitive values render masked. `POST /reveal` returns one value to a caller who holds the kind's permission, and every grant and every refusal writes an audit row with no value in it.
- Staff (`platform.reveal.sensitive`) can reveal the organization tax number, commercial register, pharmacist license, phone and email (exception E9), and the gateway admin username.
- Suppliers (`vendor.reveal.customer_contact`) can reveal `branch.phone`, but only for an order their own organization shipped.
- The buyer branch phone is masked on the supplier order list, the dashboard order preview and the order detail page. The delivery screens show it in clear with a `tel:` link so the driver can call (owner decision, 2026-11-08).
- Gateway passwords, virtual keys, AI provider keys and ERP keys are never rendered and never revealable.

## Orgasoft order feed and item codes (2026-11-10)

**Short ids.** Every id Dawa24 returns is at most 20 characters of `0-9 A-Z a-z _ -`, because Orgasoft fails on longer values.

- `X-Request-ID` and `requestId`: 16 hex characters. An inbound id is kept only when it fits the same shape (1 to 20 characters); otherwise a new one is made.
- `syncId` and `statusUrl`: the decimal `erp.sync_batches.id`. The UUID form that older syncs were given is still accepted on input.
- `variantId` (offers, sales and purchase lines, purchase errors): the decimal `catalog.product_variants.id`. Purchase `lines[].variantId` accepts a JSON string or an integer.
- `nextCursor`: the decimal id of the last row. The old base64 `v1:` token is still accepted on input (`DecodeCursor`).
- `erp.ParseShortID` reads the numeric form. `VariantOfferAsSystem` (E6) takes the id or the legacy public id.

**Item codes.** `erp.item_codes` (migration 260) maps a buyer organization and a variant to the buyer's own item code.

- `POST /orders/purchase` accepts `lines[].code` (aliases `itemId`, `itemCode`), a string or a number, trimmed, 1 to 64 characters. A refusal names `details.field = "lines[n].code"` with `n` counted from 0.
- `FinishIdempotency` upserts every coded line in the transaction that writes the order, under the buyer's tenant. A repaired order (stale reference) stores no codes.
- The purchase feed reads the code through `erp.item_codes` pinned to the buyer organization. The join must not rely on RLS, because the statement runs as system (E7). No retention: a mapping, not a log.
- Sales items keep the supplier's code from `erp.product_links`. The Orgasoft product sync accepts `externalProductCode`, `itemId`, `itemCode`, `productCode` and `code`; when a row has more than one, the order is `externalProductCode`, `itemId`, `itemCode`, `productCode`, `code`, and the first non-empty one wins. The result does not depend on map order.

**Orgasoft feed.** `GET /erp/v1/orgasoft/orders/sales` and `GET /erp/v1/orgasoft/orders/purchase` use the same scope, checks, filters and paging as the two order lists.

- The body is a bare array in the shape Orgasoft gave. One entry per supplier shipment on sales; one per order on purchase.
- The next page is in `X-Next-Cursor`, absent on the last page. Errors keep the envelope.
- Money is written from `money.Amount.String()` as a raw JSON number, so `265.00` stays `265.00`. `discount` is `erp.DiscountPercent(price, unit)`, integer math only. `price` is `list_price` when it is positive, else `unit_price`.
- `orderId`, `pharmacyCode` and item `code` are a JSON number when they are plain digits without a leading zero, a string otherwise, and null when empty (`orgasoftScalar`).
- Sales `pharmacyId` is the buyer organization; `pharmacyNumber`, `pharmacyAddress` fall back from the branch to the organization; `pharmacyCity` is the branch's city in English, else Arabic. Purchase entries describe the ordering pharmacy (the key's own organization and branch) and carry `pharmacyCode` null.
- `dawa24_app` can read `platform_admin.cities` (reference data granted by migration 222), so the city join needs no fallback.
- **To confirm with Orgasoft:** purchase entries describe the ordering pharmacy, and `pharmacyCity` uses the English city name.

**Acknowledgement.** The Orgasoft decoder reads `orderId` as an order number (a JSON number or a string). It reads `erpOrderId` and `orgaOrderId` as the ERP reference, after the existing keys.

**Named exceptions.** E6 (`ListOffersAsSystem`, `VariantOfferAsSystem`) and E7 (`ListPurchaseShipmentsAsSystem`) now read the numeric id and the buyer's item code as described above. No new exception was added.
