## Security

### The Gateway administrator credential

`platform_admin.system_settings['gateway_configuration'].api_key` held
`postgres:<password>` — the production PostgreSQL superuser credential.
`gateway.NewAdminClient` splits that on the colon and sends it as HTTP Basic
auth to `api.muhiya.com` on every provisioning, plan-listing, usage and log
call. It had been doing so since the field was filled in.

`ValidateAdminCredential` already existed and already rejected this shape, but
it only ran on save, which protects nothing already stored.

- `GatewaySettings.AdminCredentials` now returns empty for a value that fails
  validation, so a bad credential cannot leave the process through any caller,
  and `CanProvision` reports false so callers degrade to their fallback.
- The connection-test endpoint validates the credential typed into it, on the
  same terms, before opening a client.
- The stored value was cleared in the live database. The organization's virtual
  key (`sk-virt-…`) was left intact, so AI completions still work; only Gateway
  *management* calls are disabled until a real administrator credential is
  entered.

**Still required, and only you can do it:** rotate the PostgreSQL password and
the Gateway administrator credential. The old password was transmitted to a
third-party host repeatedly and was pasted into an AI session. Clearing the
field does not un-send it.

### Content-Security-Policy

`script-src` no longer names `unpkg.com`, `cdnjs.cloudflare.com` or
`cdn.jsdelivr.net`, because nothing is loaded from them any more. `default-src`
dropped its blanket `https: data: blob:`, `connect-src` dropped `http:` and the
websocket schemes, and `object-src 'none'` and `frame-ancestors 'self'` were
added.

`'unsafe-inline'` and `'unsafe-eval'` remain and are load-bearing: 56 inline
`<script>` blocks live in the templates, and Alpine 3 compiles expressions with
`new Function`. Removing them means moving those blocks into `app.js` and
switching to Alpine's CSP build. That is written down in the middleware rather
than implied away.

## Database

Four migrations, all applied to the live database.

**`149_rls_gap_closure`** — nine tables carrying `organization_id` had no
row-level security at all, four of them holding money or identity records.
They now have `ENABLE` + `FORCE` and a `tenant_isolation` policy, following the
existing convention that a NULL organization means a platform-owned row.
Separately, 76 tables had RLS enabled but not forced; every table in this
database is owned by `postgres`, so without `FORCE` any connection as the owner
read across tenants silently.

Verified after the fact by connecting as `dawa24_app` and counting: with no
tenant context it sees 26 of 32 audit rows, 0 of 36 documents and 8,284 of
10,026 match decisions; with `app.is_system` set it sees all of them. That is
the intended behaviour, and it confirms the policies actually bind. The only
code that reaches `db.Pool()` directly is River's queue driver, which operates
on unprotected `public.river_*` tables.

**`150_foreign_key_indexes`** — Postgres creates no index for a foreign key, so
each of the 35 unindexed ones meant a sequential scan on every join through it
and on every delete of a referenced row. Twenty-two of the thirty-five were in
`promo` and `smartorder`. `ingest.catalog_import_rows` has 77,054 rows and had
three of them.

**`151_duplicate_index_cleanup`** — nine indexes duplicating another on the same
table, columns and predicate. In each case the survivor is the one that also
enforces a constraint, or the one whose name says what it is for.

Indexes that are merely *unused* were left alone. Thirty have never been
scanned, which is suggestive but not conclusive — a feature nobody has exercised
cannot have used its index — and `pg_stat_statements` cannot be installed on
this instance because `shared_preload_libraries` is empty and only a server
restart can change that. **Ask Elestio to add it.** Query optimisation without
it is guesswork.

**`152_retire_dead_tables`** — twenty tables that were empty in production *and*
referenced nowhere in Go or templ. Both conditions had to hold; 47 tables that
are empty but still referenced were left in place. Three that met both
conditions were also kept because a live table still points at them by foreign
key (`billing.payment_integrations`, `inventory.father_user_temparte_warehouses`
and, transitively, the table it anchors). The down migration recreates all
twenty with columns, types, defaults and primary keys, generated from the live
schema before the drop; it does not restore their foreign keys or secondary
indexes, and says so.

### Migration drift

`schema_migrations` records version 48, `seed_realistic_data`, applied on
17 August. Its file no longer exists. The runner checksums applied migrations
but iterates over *files*, so a migration present only in the ledger was
invisible to it: this database could not be rebuilt from the repository and
nothing said so.

`(*DB).Orphans` reports the condition, `migrate` logs it at start-up, and
`cli migrate-status` prints it and exits 3. It reports rather than refuses,
because refusing to boot would strand a running deployment over a file that is
already gone.

**Still open:** either reconstruct migration 48 or write it off in `docs/adr/`.

## Frontend

- **Vendor assets are served from this application.** htmx 1.9.10, Alpine 3.13.5
  and Leaflet 1.9.4 were loaded from unpkg and cdnjs on every request; Alpine and
  Leaflet carried no integrity attribute. All four downloads were verified
  against the SRI hashes that were pinned in the templates before being moved
  (htmx sha384, Leaflet CSS and JS sha256 — all matched).
- **Leaflet is no longer on the critical path.** It was requested by every page
  in the platform and is used by two. `app.js` gained `ensureLeaflet`, which
  injects it when a map element is present and reports a failure on the element
  instead of leaving an empty box. The suppliers page was loading it a second
  time from unpkg and now shares the same loader.
- **Asset URLs carry a content hash.** `ui.AssetURL` computes it from the
  embedded file and `layouts.Asset` is installed with it at start-up. The
  hand-typed version strings had already drifted — stylesheets said
  `?v=2026082903` while `app.js` said `?v=2026082901`, so a CSS change could
  ship without the JavaScript that belonged with it.
- **Twenty tables were rendering unstyled.** Fourteen carried `class="table"`
  and six `class="b2b-table"`; neither class is defined in any stylesheet, so
  those tables fell back to browser defaults — no header treatment, no row
  borders, no hover, no dark-theme colours. They now use `.data-table`, and the
  inline declarations that restated what `.data-table` already provides were
  removed with them. Every table in the platform now uses one contract, except
  four with their own defined styles (invoice print, savings, preview).
- **311 inline style attributes removed** by mapping exact repeated values onto
  utility classes (five more went with the table fix above, 316 in total). Thirteen existing utilities covered most of it; seven new
  ones were added for patterns that appeared ten or more times, each documented
  with the count it replaced. Only exact whole-attribute matches were rewritten,
  so nothing changed visually.
- **Four tests now guard the layout**: no CDN hosts, no Leaflet in the head,
  every local asset URL carrying its file's hash, and the shell always
  rendering. `internal/ui/layouts` previously had no tests at all.

The `Base` template used to wrap its entire body in `if site != nil`.
`GetSiteSettings` never returns nil — it falls back to a complete default — so
that branch could not fire. It was removed rather than left implying a failure
mode that does not exist.

## One render path instead of two hundred

`UIHandler.renderPage` replaces 201 copies of the same three lines — set the
content type, render, log the error. Copies are how a response path drifts: a
handler that forgets the content type serves HTML as `text/plain`, and one that
drops the error check loses the only signal a page failed halfway through. The
19 that remain are genuinely different — an explicit status code, extra log
fields, a fallback to `renderError` — and were left rather than forced into a
shape that does not fit.

The helper documents why a render error is logged and not surfaced: by the time
templ fails, bytes are usually already on the wire, so the response cannot
become a 500. Handlers that need to fail *before* rendering still call
`renderError`.

## The three god files are gone

`admin_handlers.go` was 3,149 lines, `customer_handlers.go` 2,223,
`vendor_handlers.go` 1,997. They are now 121, 434 and 142, with their contents
moved into 30 files named for what they do — settings, approvals, products,
billing, geography, developers, audit, institutional, documents, users,
commerce; cart, checkout, orders, branches, employees, notifications; variants,
team, inventory, offers, ingest samples.

Nothing was edited in the move. Declarations were relocated verbatim inside the
same package, so no call site, signature or visibility changed; `goimports`
pruned each new file's imports. Twelve more files were split the same way,
including `handlers.go` (routes now separate from the request helpers and the
constructor) and `public_handlers.go` (authentication separated from the public
pages).

The largest file in `internal/ui` is now 543 lines. The oversized *count* only
moved from 101 to 93 because several of the new files are still in the 400–550
band — but no file in the web layer is now beyond one sitting's reading.

## Emoji, and why a blanket delete was the wrong tool

The first attempt deleted every decorative emoji. It broke the build, and the
way it broke was the useful part: an `if` branch whose only content was a lock
emoji became an empty branch, which templ rejects outright, and a delete button
whose only content was a wastebasket became an invisible control. Deleting
decoration is safe; deleting the *only* content of an element is not.

The second attempt separates three cases:

- **Sole content of an element or branch** → replaced with the matching icon
  from `internal/ui/components/icons.templ`. 398 of these.
- **Inline beside text** ("📦 Orders") → deleted, taking at most one following
  space so the surrounding words keep their spacing. 600 of these.
- **No icon means the same thing** → left alone. 46 remain, mostly status dots
  (🟢 🔴) and one-off glyphs that want a design decision rather than a sweep.

Decoration was also removed from four i18n catalogue files. A translated string
should not carry an emoji: it is not translatable, it is not part of the
meaning, and it appears in every language.

**Deliberately not touched:** `internal/ui/visitor.go` stores country names with
flag emoji (`"مصر 🇪🇬"`), and `platform_admin/postgres/visitors.go` has SQL that
compares against those exact strings. Stripping one without the other would
silently stop matching rows that are already in the database. Structs with an
`Icon string` field holding an emoji (`pages/wizard.go`,
`admin_import_wizard.go`, `ingest/catalog_import.go`, `identity/domain.go`) were
also left: converting them means changing every render site, which is a change
per site rather than a sweep.

## N+1 queries: none left, and two of the five were misjudged

The favourites page, the public jobs list and the admin jobs list were genuinely
unbounded — one query per row of whatever the page displayed — and are batched.

The vendor coverage form called `GetCity` once per selected city; a vendor
covering a governorate submits dozens at a time. It now reads the 351-row city
table once and indexes it.

The fifth, in `compare_results_handlers.go`, turned out not to be an N+1 at all:
an explicit guard three lines above caps the loop at ten files. Recorded here
rather than quietly dropped from the count.

# Fourth pass — component library and inline styles

Run alongside another agent that was adding a courier / delivery / MFA feature
to the same tree. Only `.templ` and `.css` files were touched here, so the two
did not collide.

## The component library now has no dead code

148 component declarations, of which 50 were reported unused. Two corrections
came out of looking properly:

- **14 of the 50 were false positives.** The gate only counted references from
  `pages/` and `layouts/`, so components used by *other components* looked dead:
  `ThemeToggle` uses `IconSun`/`IconMoon`, `LanguageToggle` uses the flag icons,
  `CapsuleAssistant` uses `IconSend`/`IconPaperclip`, `Modal` uses
  `SkeletonText`. The gate was rewritten to count intra-component references,
  and now enforces a ceiling of **zero** rather than a number.

- **The remaining 36 were not waiting to be adopted. They were redundant.**
  The evidence is in how pages actually write markup: `form-input` appears 657
  times, `form-label` 620, `btn` 1,257, `avatar` 106, `tabs-nav` 27 — as CSS
  classes, directly. The design system in this codebase lives in CSS, not in
  templ components, and it works. `FormInput`'s fixed signature (label, name,
  type, value, placeholder, required) cannot express what 865 real inputs need —
  htmx attributes, Alpine bindings, `min`/`max`, `readonly` — which is why
  nobody adopted it in the first place.

So they were deleted, not adopted: 20 whole files (`forms`, `buttons`, `tabs`,
`datatable`, `dropdown`, `drawer`, `combobox`, `datepicker`, `daterangepicker`,
`filedropzone`, `commandpalette`, `imagegallery`, `pricetag`,
`quantitystepper`, `rating`, `review_modal`, `timeline`, `toast`, `avatar`,
`breadcrumbs`) plus `ConfirmModal`, `PaginationNav`, three unused icons and four
skeleton variants. About 1,100 lines of speculative abstraction.

**Their CSS was kept.** `.data-table`, `.form-input`, `.btn`, `.spinner`,
`.skeleton` and the rest stay in `components.css`, because that is the contract
pages actually use. Nothing rendered changed.

Component declarations: 148 → 108, every one of them referenced.

## The "100 inline SVGs" finding was wrong

98 of those 100 *are* `internal/ui/components/icons.templ` — the icon library
itself. Only two exist outside it, and both are correct: a progress ring in
`smart_order_steps.templ`, which is a data visualisation rather than an icon,
and the brand logo in `invoice_printable.templ`, which hard-codes its colours
because a print stylesheet cannot rely on theme tokens. Nothing to do; the
original metric was measuring the wrong thing.

## Inline styles and emoji

A third sweep removed 156 more inline style attributes, mapping exact repeated
values onto utility classes. Two of them replaced a literal with the token that
equals it — `border-radius:8px` is exactly `--radius-md`, and
`border-radius:var(--radius-lg)` is what `.rounded-lg` already sets.

Several sizes and gaps in the new utilities (0.775, 0.8, 0.825, 0.85, 0.9rem;
0.4, 0.6, 1.15rem) sit *off* the scales in `tokens.css`. They are preserved
verbatim rather than snapped to the nearest token, and said so in the
stylesheet: silently moving a value is not a refactor. Reconciling them is a
typography and spacing pass of its own.

The emoji converter was re-run with an extended icon map (clock, monitor,

# Fifth pass — the reason screens looked unfinished

## The finding

Every class name used in `internal/ui/**/*.templ` was diffed against every class
name declared in `internal/ui/static/css/*.css`.

**617 classes were used and never defined, across 4,199 occurrences.**

They were not exotic. The single most-used class on the platform is
`.form-label`, at 626 uses, and it did nothing at all. `.form-group` (240) did
nothing, so no form field had spacing between label and input. `.alert`,
`.alert-danger`, `.alert-success` and `.alert-warning` (104 between them) did
nothing, so **every validation failure and every save confirmation on the
platform rendered as unstyled body text**. `.table-responsive` (9) did nothing,
so a table wider than its column pushed the whole page sideways instead of
scrolling inside its own container. `.overflow-y-auto` did nothing, so the
catalogue's category filter — which has an inline `max-height: 180px` — clipped
its list with no way to reach the rest.

The markup was written as though a utility framework were loaded. None is. That
is the reason screens looked half-finished for no visible reason in the
template, and why a fix applied to one page never generalised to another.

## The fix

A new stylesheet, `internal/ui/static/css/foundations.css`, declares what the
markup has always asked for, built entirely from the tokens in `tokens.css` so
all of it follows the theme:

- **Form primitives** — `.form-group`, `.form-label`, `.form-hint`,
  `.form-error`, `.form-check`, and the compact `.input-sm` variants.
- **Alerts** — four tones from the semantic ramps, with dark-theme overrides
  because the 600-weights go muddy on a tinted dark ground.
- **The spacing scale, completed** — `utilities.css` had `m-*`, `mb-*`, `mt-*`
  and `p-*`/`px-*`/`py-*` but no `pt`/`pb`/`ps`/`pe` and no half steps, so 577
  spacing attributes did nothing. The logical `ps`/`pe`/`ms`/`me` pairs matter
  here: this interface is RTL first.
- **Type scale gaps** — `text-2xs` (140 uses), `text-4xl`, the `leading-*` and
  `tracking-*` families.
- **Palette utilities** — the ramps existed as tokens and were never exposed as
  classes. Includes the `border-slate-200/80` opacity forms the templates write,
  spelled out with `color-mix`, and dark-theme mappings so a literal
  `bg-slate-50` does not render white-on-white.
- **Layout helpers** — `position-*`, `overflow-*`, `cursor-pointer`,
  `text-truncate`, `shadow-2xs`, `z-*`, and the logical `start`/`end` insets.
- **Interaction states** — the `hover:` forms, with the colon escaped, since it
  is a class-name character here rather than a pseudo-class.
- **Component classes the markup expects** — `.stat-card-label` (117 uses) and
  `.stat-card-sub` beside the `.stat-card-title` that already existed;
  `.b2b-pagination*`, which the pagination component emits and nothing styled;
  `.filter-tab`, `.status-dot`, `.map-canvas`, `.header-row`, `.hover-lift`.

`.map-canvas` is worth calling out: without a height the map container collapsed,
so Leaflet was initialising into a zero-height box.

**Result: 4,199 → 771 occurrences (82%).** The remainder is a long tail of
twenty-two uses or fewer, plus artefacts of the measuring script — templ
ternaries inside `class="…"` leave operators behind that look like class names.

## Modal lag

The admin modals stalled for a beat on open. Four causes, all fixed in
`app.js` and `components.css`:

1. **Blur over blur.** Every `.glass-panel` carries `backdrop-filter`, a page
   holds dozens of them, and the overlay adds one more on top. It is the most
   expensive property in the stylesheet — each instance forces its own
   compositing layer and re-filters every frame — so the browser was blurring a
   page that was already blurred. `body.modal-open` now switches the background
   blurs off while a modal is open. None of that work was visible through the
   overlay anyway.
2. **No scroll lock**, so the page scrolled behind the overlay. Locked by
   position rather than `overflow: hidden`, so the layout does not jump.
3. **A synthetic `window.resize` fired 100ms after every open**, running every
   resize listener on the page — charts, tables, sidebar, Leaflet — whether or
   not the modal contained anything resizable. It now fires only when the modal
   actually holds a map.
4. **Two modals open at once** each restored the scroll on close. An open count
   keeps the lock honest.

## Sponsored placements

Three different treatments existed: the product card and the catalogue table
each inlined the same amber hex triple — which does not follow the theme, so it
stayed pale-yellow-on-brown in dark mode — and the offers grid used a fourth
style with a shield icon. The wording differed too: "ممول" in one place,
"ممول — رعاية" in another.

All three now use `components.SponsoredBadge`, with tokens for both themes. The
tone is deliberately quiet: a sponsored label is a disclosure, not a promotion,
and on a product card it sits directly beside a discount badge — the previous
amber competed with that and read as a second offer. A promoted card also gets
`.is-sponsored`, which draws an inline-start rail, applied conditionally so the
rule never touches an organic result.

The underlying flow was already sound — `RankedSponsorshipsForProducts`,
`IsSponsored`, the ranking sort that floats paid placements — and was left alone.

`templ generate` is clean and every change here is CSS, templ or JavaScript.

The Go build is **red**, from a concurrent change in another session:
`internal/modules/catalog` is mid-way through making `CostPrice` a

# Sixth pass — an offer could not be bought

## What was wrong

`POST /cart/add-offer` failed on every click, for every offer, with a generic
"could not add" message.

The first read of the code suggested the offers simply had no products. The
owner corrected that, and the correction is the whole point: **the products
attached to an offer are a manifest — what the buyer receives for the offer's
price — not separately purchasable lines.** An offer is sold as one unit at
`promo.offers.total_price`.

The handler did the opposite. It walked the manifest and added each product as
its own cart line at its own price, which is a different transaction from the
one the supplier published. And because the sole offer in this database has no
manifest rows, there was nothing to walk: `sp.Products` was empty, `baseOffer`
was only fetched when the *other* lookup failed so it stayed nil, both branches
were skipped, and the handler fell through to its failure message having done
nothing at all.

Underneath that, `commerce.cart_items` could not represent an offer even in
principle: `product_id` and `product_variant_id` were both `NOT NULL`.

## The fix

**Migration 155** makes both product columns nullable and adds a check
constraint so a line is one of exactly two shapes — a product line (both product
references set) or an offer line (`offer_id` set, both product references null).

It also adds a partial unique index on `(cart_id, offer_id)`. The existing
upsert conflicts on `(cart_id, product_variant_id)`, and two NULLs are distinct
in Postgres, so that target can never match an offer line: adding the same offer
twice would have inserted a second row instead of raising the quantity.

`commerce.order_lines` needed nothing — it already allowed null product
references and carries its own `product_name`, so an offer survives into the
order as a normal line.

**The handler** now resolves the offer's price and owner and adds one line.
An offer with no price is refused with its own message rather than sold for
nothing.

**Cart lines are addressed by their own id.** Removal and quantity changes were
keyed off `product_variant_id`, which an offer line does not have, so an offer
in the cart could not have been removed or re-quantified. `RemoveCartLine` and
`SetCartLineQuantity` take the line id, which both shapes have; the variant path
stays for existing markup. Offer lines skip the stock check on quantity change,
because there is no variant whose stock could answer that question.

**The read path** needed one change: an offer line's display name comes from the
offer title. The organization already resolved through the offer, and the joins
were already `LEFT`.

## Verified against the live database

Not by reading the code: by running it.

- An offer line inserts with both product references null — accepted.
- Adding the same offer again raises the quantity to 3 and leaves one row.
- A line with neither a product nor an offer is rejected by the check
  constraint.
- The cart read query returns the offer line with the offer's Arabic title as
  its name and the supplying organization resolved through `promo.offers`.

Test rows were removed afterwards; the cart tables are back to empty.

## Along the way

`i18n.Translate` was added for keys chosen at runtime. `T` forwards to a
formatter, so `go vet` reads it as printf-style and rejects a non-constant key
even with no arguments. `Translate` performs the same override-then-default
lookup without the variadic path. Six repository mocks gained the two new cart
methods.

Build, `go vet` and 69 packages of tests are green.

# Seventh pass — errors that nobody could see

## What was wrong

`platform_admin.error_logs` had eighteen well-chosen columns, a `LogError`
writer, a `ListErrorLogs` reader with filters, and an admin screen at
`/admin/developers?tab=errors` to display them.

The table had **zero rows**, and always would have. Nothing ever called
`LogError`. Every failure on the platform ended at a `slog` line in a container
log: a 500, a database timeout, a panic, a failed AI call. None of it reached
the screen built to show it, and none of it was searchable by the people who
needed it.

## What was built

A new platform package, `internal/platform/errtrack`, and three capture points.

**Why a package rather than a call at each error site.** Three places already
turn a failure into a response — `httpx.Error` for API replies, `httpx.Recover`
for panics, and the UI's own error page — each logging in its own shape. Adding
a database write to each would have coupled the platform layer to a business
module, which the module boundaries forbid. So: an interface in `errtrack`, an
implementation in `cmd/server`, wired at start-up. The same shape the asset
resolver and the gateway settings already use here.

Three properties drove the design, and each is a decision not to do the obvious
thing:

- **A request never waits on error logging.** `Capture` hands off to a buffered
  channel and returns. When the queue is full, events are dropped and counted
  rather than allowed to slow the request down: the user's request matters more
  than the record of its failure.
- **Recording a failure never becomes a failure.** The writer swallows sink
  errors into `slog`. That is the one place the error stops.
- **A failure loop cannot fill the table.** Identical errors are throttled by
  fingerprint for thirty seconds. The fingerprint deliberately excludes the URL
  path: the same nil dereference reached from three URLs is one bug.

**Captured now:**

| Where | What | Level |
|---|---|---|
| `httpx.Recover` | panics, with stack | CRITICAL |
| `httpx.Error` | API failures at 5xx | ERROR |
| `ui.renderError` | every server-rendered page failure at 5xx | ERROR |

Below 500 is deliberately **not** captured. A validation refusal, a missing
record, a permission the caller does not hold — those are a working system's
normal traffic, not defects, and recording them would bury the real faults.

**Two details worth stating.** `PanicOrigin` walks a panic stack and picks the
first frame in application code, skipping the runtime and the recovery
middleware, because that is where the bug is rather than where it was caught.
And the payload column records the request's *shape* — status code, request id —
never its body: a body can carry a password, a token or a national ID, and this
table is read by staff, exported and kept.

**An import cycle shaped one decision.** `authctx` already imports `httpx`, so
`errtrack` cannot read the actor from a context directly. The actor resolver is
a function installed at start-up, which leaves `errtrack` free of dependencies
on the rest of the platform.

## Verified

Nine unit tests cover the properties above, including that `Capture` does not
block when the queue is full and that a failing sink cannot deadlock the writer.

End to end, against the live database: a probe built the real tracker over the
real sink and reported one event. The row appeared in
`platform_admin.error_logs` with its level, message, exception class, file, line,
method, path and status intact, and was removed afterwards. The table is empty
again and the wiring is proven.

Build, `go vet`, `gofmt` and 70 packages of tests are green.
